Why two components and not one

This is the most instructive design decision in the whole physiology layer, and it makes a good answer to "how do you avoid flattering your own algorithms?"

An additive glucose inflow is dose-cancellable. A closed-loop controller can simply give more insulin and completely erase it — which is not how the dawn phenomenon behaves in patients. Clinically, dawn is in substantial part a resistance phenomenon: counter-regulatory hormones blunt insulin's effect, so the same dose achieves less, and as resistance rises each additional unit buys progressively less. Modelling dawn only as an inflow therefore lets an algorithm look better overnight than it would be in a person. F16 exists to remove that free win.

\(f_{\mathrm{dawn}}\) is capped strictly below 1.0 so that insulin action can never be abolished entirely — at \(f = 1\) the glucose trajectory would become independent of every dose the algorithm gives, which is a degenerate test, not a hard one.

△

Phenomenological, and off by default. The literature supports a circadian fall in insulin sensitivity toward early morning. The raised-cosine shape and the peak values are IINTS scenario heuristics, not coefficients estimated from any cited study, and this is not a cortisol or growth-hormone model. Both parameters default to zero, so the default configuration reproduces the pre-existing behaviour exactly.

Likely jury questions

Why a raised cosine rather than a step or a sine?

A step gives a discontinuous glucose rate at 04:00 and 08:00, which is both unphysiological and hard on the integrator. A plain sine over the window would not reach zero at the edges. The raised cosine is \(C^1\), is exactly zero outside the window and exactly 1 at the midpoint, and needs only the two parameters a user already sets.

Where does F16 enter the equations?

Through the sensitivity multiplier, never through glucose directly. In Hovorka it multiplies \(k_{b1}, k_{b2}, k_{b3}\) — that is, \(S_{IT}, S_{ID}\) and \(S_{IE}\) alike, so transport, disposal and hepatic suppression all lose sensitivity together. In Bergman it multiplies \(p_3\), because \(S_I = p_3/p_2\) and scaling \(p_3\) scales sensitivity itself rather than the momentary effect.

△

These are not hormone concentrations. The registry is blunt: "The stress branch is not a cortisol/adrenaline concentration model." Likely jury questions

Does your model reproduce post-exercise late hypoglycaemia?

Yes, and it emerges rather than being coded. The mechanism is the asymmetry in F09: GLUT4 activates at 0.05 min⁻¹ but deactivates at 0.01 min⁻¹, so elevated insulin-independent uptake persists for hours after \(H_{\mathrm{ex}}\) itself has returned to zero with its 10-minute time constant. Whether the magnitude is right is unvalidated.

Exercise tripling insulin sensitivity seems extreme.

It is at the top of the plausible range and it applies only at maximum intensity, which a scenario has to request explicitly. It is a heuristic coefficient, and I would treat any quantitative result that depends strongly on it as a sensitivity finding rather than a conclusion. The direction is well supported; the factor is not calibrated.

Scope boundary — state this before anything else in this area. IINTS-AF contains no immune-cell model, no beta-cell mass dynamics, and no PD-L1 pharmacodynamics. If a jury member asks how PD-L1 expression affects your simulation, the correct and complete answer is: it does not, and the SDK does not claim it does.

What this can and cannot support

Can express
"If a graft restored a given fraction of glucose-responsive secretion, and that fraction decayed exponentially, what would the glucose trajectory look like?" — a what-if with an explicit, single assumption.
Cannot express
Autoimmune attack kinetics, T-cell or macrophage populations, checkpoint signalling, inflammation, graft revascularisation, or any mechanism by which an immunomodulatory intervention would change \(k_{\mathrm{reject}}\).
Guardrail
The patient factory raises if graft parameters are passed to a backend that does not implement them, rather than silently ignoring them — so a result can never come from a configuration that was quietly dropped.
Honest framing
\(M_{\mathrm{graft}} = 1.0\) is an abstract functional fraction. The source comment states directly that 100% "is not a clinical cure claim."
Likely jury questions

You mention regenerative medicine. What is the immune model?

There isn't one, and I would not want to imply otherwise. There is a single exponential decay constant on an abstract graft-survival fraction. It is a placeholder that lets the glucose model respond to a declining graft; it contains no immunology. Anything stronger would need cell-population dynamics the SDK has neither the data nor the validation to support.

Could you extend it to model immunosuppression?

Structurally, yes — \(k_{\mathrm{reject}}\) is exactly the hook a pharmacodynamic term would attach to, in the same pattern as the glucagon effect compartment. What is missing is calibration data, not code. I would rather ship an honest one-parameter placeholder than an elaborate model with no numbers behind it.

△

Not a motor or fluid model. The 70/30 miss-versus-extra split is a configurable research assumption, explicitly "not rotor physics". Occlusion, priming, bubble formation, cannula kinking and temperature effects are not modelled. This is a transparent bench abstraction of dose-domain uncertainty.

Likely jury questions

Why model pump error at all — isn't it negligible?

Per dose, yes. Over a day it is not, because the error is biased rather than zero-mean: with the default asymmetry the pump systematically under-delivers by about 0.8% of commanded insulin. A controller tuned against a perfect actuator will slowly run higher than it expects, and that only shows up if the actuator is modelled.

Two separate lags — do not conflate them

\(\tau_{\mathrm{ISF}}\) is the time constant of a first-order interstitial compartment; lag_minutes is an explicit transport dead time applied before it. The source is emphatic that these "are separate assumptions and should not both be fitted to the same observed total CGM lag." Doing so would double-count the delay.

Why the noise is not white

White noise is trivially filtered — a controller could average it away in two samples. Real CGM error is strongly autocorrelated: a sensor reading 15 mg/dL high now will still read high in five minutes. The SDK offers two colouring models, and the default is the harder one:

  • AR(1): \(\varepsilon_k = \phi\,\varepsilon_{k-1} + \eta_k\) with \(\eta_k \sim \mathcal{N}(0,\sigma\sqrt{1-\phi^2})\). The \(\sqrt{1-\phi^2}\) factor is what keeps the stationary variance equal to \(\sigma^2\) regardless of \(\phi\) — without it, raising the correlation would silently raise the noise amplitude too.
  • Fractional-noise approximation (default): three superposed AR(1) processes at \(\phi\) = 0.5, 0.85, 0.98, weighted by scale\(^{H-0.5}\) and normalised. This produces long-memory behaviour closer to real sensor drift. The source is explicit that it is "a compact CGM-noise approximation, not an exact fBM sampler."

Compression lows

A distinctive failure mode worth mentioning unprompted: lying on a sensor restricts local perfusion and produces a transient false low. The model triggers it probabilistically only when true glucose is already below compression_low_max_glucose (140 mg/dL), subtracts 12–28 mg/dL for 3–8 steps, and flags the reading compression_low. This is the single most dangerous CGM artefact for a closed loop, because it asks the controller to suspend insulin in a patient who does not need it — or, worse, looks like a hypo that the controller then over-treats.

Likely jury questions

Is 8.5 mg/dL a realistic noise level? What MARD does that correspond to?

At a mean glucose around 145 mg/dL, a 6.3 mg/dL mean absolute error is roughly 4–5% — better than most commercial sensors, whose MARD is typically 8–10%. So the default is if anything optimistic on noise, though the lag and compression-low behaviour make it harder in other respects. I would not quote it as a MARD claim: MARD is defined against reference blood samples over a specific study protocol, and this is a simulated error statistic.

Can a controller "cheat" by reading true glucose?

No. The simulator passes glucose_to_algo_mgdl to the algorithm and keeps glucose_actual_mgdl for scoring only. The results frame contains both columns, which is what makes the error analysis in this chapter possible — but the algorithm interface never receives the true value.

Is the noise reproducible?

Yes. The sensor holds its own seeded NumPy generator and stores its initial bit-generator state, so reset() reproduces the identical noise realisation. Sensor state — including the RNG state and the full history buffer — is part of the saveable snapshot.
