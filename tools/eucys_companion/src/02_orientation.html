The four claims, kept separate

A great many hard questions are really asking which of these four you are claiming. Keep them apart and the answers stay short and defensible.

ClaimWhat would establish itStatus in IINTS-AF
Mathematical correctness The code integrates the stated equations; conservation, units and bounds hold. Asserted and tested. 175 test modules; every flux the ODE writes is pinned against the published schema.
Physiological plausibility Trajectories stay inside documented research envelopes and respond in the right direction. Asserted, with tools to check it. Envelope violations raise rather than clip.
Experimental validation Parameters identified against measured data from clamp or CGM studies. Partial. Structure and some parameter ranges come from literature; the IINTS scalars do not.
Clinical validation Prospective evidence that results transfer safely to people. Not claimed anywhere. This is a bench, not a device.
!

The one sentence to have ready. IINTS-AF is a research and educational simulator. It is not a medical device, it has not been clinically validated, and no number it produces may be used to determine a real insulin dose. Saying this first costs nothing and makes every subsequent technical claim easier to defend.

Evidence classes

Each of the 16 registered formulas carries an evidence class in the source itself (formula_registry.py). This is the vocabulary to use when asked "is this real physiology or did you invent it?" — the honest answer is already in the code.

System architecture

Where numbers come from, and — more importantly — which component is allowed to produce them.

The step loop

One simulation step is five minutes by default. Everything below happens in a fixed order, and the order is the safety argument: the patient's true state is never visible to the algorithm, and the algorithm's output is never delivered without passing an independent check.

1 · TRUTH
Patient ODE state
19 states, hidden
2 · SENSE
CGM model
lag + noise + drift
3 · GATE
Input validator
fail-soft damping
4 · DECIDE
Algorithm
candidate dose
5 · SUPERVISE
Independent supervisor
clamp or reject
6 · ACTUATE
Pump model
quantise + error
7 · INTEGRATE
solve_ivp RK45
next state

Steps 2 and 6 are the reason a controller that looks excellent against perfect information can still fail here: it never receives perfect information, and it never delivers exactly what it asked for.

Numeric authority

The SDK defines an explicit authority order — which component may produce a number that reaches the actuator. This is the answer to any question beginning "but what if the AI…".

#ComponentAuthority
1Mechanistic patient modelsCalculate physiological state in explicit code.
2Deterministic controllersCalculate research candidates.
3Independent supervisorClamps or rejects unsafe candidates. Final word on dose.
4ML predictorsMay estimate future glucose. Cannot replace physiology or bypass the supervisor.
5Language modelsMay explain supplied evidence. No numerical, diagnostic or actuator authority.

The formula registry exports this as a machine-readable flag: ai_numeric_authority: false. A local LLM receives the formulas as immutable context with the instruction "Do not derive or solve formulas."

Determinism contract

  • The same dose payload and safety configuration produces the same result.
  • Safety configurations carry a formula version and a SHA-256 fingerprint.
  • Randomness is permitted only outside the dose-authority path, always with a recorded explicit seed and never mutating global random state.
  • Missing checkpoints, non-finite predictions and model exceptions fail closed to a deterministic fallback.
Likely jury questions

Why not just use an existing simulator like UVA/Padova?

Certified simulators answer "does this controller work". This bench answers a different question: what happens when the data and the devices are wrong — uncertified input, sensor compression lows, pump step errors, an unannounced meal. That is why the corruption arms and the supervisor ablation exist. It is a complement, not a replacement, and results here do not substitute for a certified simulator.

Where exactly could an AI model change an insulin dose?

Only by proposing a candidate at step 4, and only within the ML candidate cap (1.0 U per step). It then passes the same supervisor as every other controller. A language model sits outside the loop entirely.

Is the simulation reproducible?

Yes, given the seed and the safety configuration fingerprint. The sensor and pump each hold their own seeded generator and can be reset to their initial bit-generator state, so a run is repeatable including its noise realisation.

Four backends share one interface. Most of this handbook documents the Hovorka backend, because it is the most mechanistic and the default for research runs.

△

Domain trap. Hovorka integrates glucose mass and divides by the distribution volume at the end (\(G = Q_1 / V_{G,\mathrm{dL}}\)); Bergman integrates concentration directly. Any term shared between them — the dawn rate, the renal loss — must therefore be multiplied by \(V_{G,\mathrm{dL}}\) in Hovorka and not in Bergman. The SDK does this explicitly, and it is a place where a careless extension silently produces a 112-fold error.

Likely jury questions

Why an ODE rather than a static or data-driven model?

Because the quantity that matters is a rate with memory. Insulin given now acts over the next four to six hours through states that persist between steps — \(S_1, S_2, I, x_1, x_2, x_3\). A static map from current glucose to dose cannot express insulin-on-board, so it cannot reproduce stacking, the single most common cause of iatrogenic hypoglycaemia. An ODE also lets every term carry a unit and a source, which a learned black box does not.

Why does the Hovorka model need 19 states when the published one has fewer?

Eleven states are the published core. The other eight are declared extensions — glucagon PK/PD (4), stress and exercise pseudo-hormones (2), HAAF memory (1), GLUT4 (1) — and each is marked extension in the compartment schema so a viewer or report cannot present them as equals to the canonical states. All of them default to inert.

How do you know the integration is accurate?

Tolerances are set roughly three orders of magnitude below sensor noise, and the 1-minute max step is well below the fastest time constant in the system (\(1/k_{a2} \approx 17\) min). The stronger argument is structural: the model refuses to continue on a negative compartment or an out-of-bounds fraction rather than silently clipping, so an integration failure surfaces as an exception instead of a plausible-looking trace.
